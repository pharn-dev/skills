## Intent

The Phargus helpers in `src/phargus` (CORE-240, S4.7) throw away good recordings, or report them wrongly, because of
input problems that happen in normal use. A recording saved by an editor with a UTF-8 byte order mark has its first
sample counted as an invalid record. A single line over 1 MiB fails the whole file, so `summarize` returns nothing for
a recording that is otherwise valid. With `--allow-logs`, an ordinary application log written as JSON (winston, pino,
or a line such as `{"type":"http"}`) is counted as a corrupt Phargus record because it shares a key name such as
`timestamp` or `type`. A capture manifest whose `quality.invalidRecords` or `quality.ignoredLogs` is missing or not a
number is accepted, and the summary can then print a `null` counter. A capture that fails before it writes any event
(an HTTP 401, a refused connection, an unknown host, a redirect) leaves `events.ndjson` and `manifest.json` in `--out`,
so a retry into the same `--out` is refused, and the error says only `fetch failed` without naming the cause.

The person wants these input problems not to cost a recording: a BOM is ignored, an oversized line costs one invalid
record instead of the file, JSON logs are told apart from Phargus records by the fields a Phargus record actually
carries, malformed manifest counters are refused up front, and a capture that wrote nothing leaves nothing behind and
says why it failed. The capture failure path stays plain and easy to extend, because SIGTERM handling is added next.
This ships as a fix in the unreleased phargus 0.1.1, with no version bump.

## Scope

**In scope:**

- The shared line reader in `src/phargus/runtime/records.mjs`: dropping a leading U+FEFF on the first line, and
  reporting a line over 1 MiB to its caller instead of throwing; its callers (`summarize` through the file reader,
  `collect --follow` in `runtime/operations.mjs`, SSE capture in `runtime/capture.mjs`) count that line as one invalid
  record.
- `classifyLine` in `runtime/records.mjs`: which JSON objects that fail record validation count as malformed Phargus
  records and which count as logs.
- Manifest counter validation in `runtime/summary.mjs` for `summarize --manifest` and
  `compare --before-manifest/--after-manifest`.
- The capture failure path in `runtime/capture.mjs` and the error print in `runtime/phargus.mjs`: removing both
  reserved files when zero events were written, and naming the fetch cause in the error message.
- Unit tests in `test/data.test.mjs`, `test/summary-regressions.test.mjs` and `test/capture.test.mjs`, including an
  in-place rewrite of the test at `test/capture.test.mjs:79`.
- `src/phargus/knowledge/tools.md` (lines 28-37) and its generated copies under `plugins/phargus`, regenerated by
  `npm run build`.
- One `phargus 0.1.1:` bullet under `CHANGELOG.md` `[Unreleased]` `### Fixed`.

**Out of scope (non-goals):**

- SIGTERM handling in capture (the next increment).
- A version bump of the phargus plugin or `src/phargus/package.json`, a release or a tag.
- Changing the 1 MiB line cap or the 64 MiB SSE response cap.
- Changing the Phargus runtime, the record schema `parseRecord` validates, or how a valid record is summarized.
- Changing what `collect` does with invalid records once they are counted.
- Removing files from a capture that wrote at least one event before it failed.
- Deleting any existing test.

## Constraints

- Node.js `>=22.18.0`, as `src/phargus/package.json` `engines` declares; the line reader keeps its 1 MiB cap per line
  and SSE capture its 64 MiB cap per response.
- Each acceptance criterion has a unit test in `test/data.test.mjs`, `test/summary-regressions.test.mjs` or
  `test/capture.test.mjs`; the closed-port test uses a closed high port, never port 1.
- The test at `test/capture.test.mjs:79` ("fails on authentication errors and preserves an error manifest") is
  rewritten in place to AC-8's behaviour, not deleted and re-added elsewhere; no test is deleted.
- Without `--allow-logs`, every line that is not a valid Phargus record still counts as an invalid record.
- `plugins/phargus` copies are produced by `npm run build`, never edited by hand.
- The capture failure path stays a single plain path that a later SIGTERM change can extend.

## Assumptions

- "Removes both files" applies to the two files the failed capture itself reserved; a pre-existing `manifest.json` or
  `events.ndjson` in `--out` is never removed, as the test at `test/capture.test.mjs:166` already requires.
- A capture that wrote at least one event and then failed keeps both files, with `termination` recorded in the
  manifest as today.
- `collect --follow` and `collect` in file mode count an oversized line as one invalid record and then apply their
  existing rule for invalid records (collection fails on corrupt data); only the cause changes from the reader's
  `input line exceeds 1 MiB` throw to the caller's invalid-record handling.
- In SSE capture, a line over 1 MiB counts once as an invalid record, and the message it belonged to is not counted a
  second time.
- The fetch cause is appended to the error message as `cause.code` when present, else `cause.message`, after a
  separator the plan chooses; Node's `fetch` reports a refused connection as `cause.code` `ECONNREFUSED`, an unknown
  host as `ENOTFOUND`, and a refused redirect as `cause.message` `unexpected redirect` (checked on Node 24.13.1 this
  run). `ENOTFOUND` has no test, because it needs name resolution; it takes the same path as `ECONNREFUSED`.
- A malformed JSON line keeps today's text test for recognizable truncated Phargus JSON; the new field rule applies to
  lines that parse as JSON objects.
- A counter that is a non-negative integer is a safe integer at or above 0, as `integer` in `runtime/records.mjs`
  already defines it.
- The `phargus 0.1.1:` CHANGELOG bullet names CORE-240.
